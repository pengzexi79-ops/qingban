## 1. 背景与动机

现状(Phase1 契约)是"发一条 → 立刻回一条"。真实陪伴场景下它有三个病:

1. **连发鬼畜**:用户连续输入时,每一条消息都触发一次模型调用,AI 对半截话反复回应;
2. **上下文浪费**:每条消息都重算全量历史,厂商 KV 缓存(TTL 内同前缀复用)完全无法命中;
3. **群聊轰群**:用户随口一句,全群每个成员都回一遍。

因此把消息链路从"推送-应答"改成"**收件-攒批-批次投喂**":AI 像人一样有"未读",攒一批再读;读完可以回,也可以不回。

### 1.1 两条铁律

- **点名即时,闲话攒批**:消息里 @ 了谁,谁立刻被调度;没 @ 的消息先存着,之后不定时再投给群员。
- **已读即归档,不重投**:喂给 AI 的消息立即标记该 AI"已读";已读消息不再进入后续任何一次模型调用,只被压缩进短期记忆。

## 2. 核心语义(单聊与群聊统一)

### 2.1 消息的双向已读标记

每条消息对"人"和"AI"两侧各维护已读状态:

| 侧 | 已读语义 | 载体 |
|---|---|---|
| 人(用户) | 在会话里看过 AI 的消息 | 会话级未读计数(现有 `conversations.unread`,`POST /read` 清零)+ 消息级 `user_read_at`(可选回执展示) |
| AI 成员 | 该成员某次模型调用已消费到哪条消息 | 每个 (会话, 成员) 一个**消费水位游标** `last_read_message_id` |

> 群聊中每个 AI 成员各有自己的游标:A 回完的话,B 眼里那条 A 的消息仍是"未读"(B 需要看群聊上下文,回批时自然拿到)。

游标语义下"某成员的未读消息" = `会话内 id > 该成员游标` 且 `非该成员自己发送` 的消息,按下发顺序拼接。单聊 = 群聊的 1 AI 特例,机制完全一致。

### 2.2 批次投喂:输入 = 人设 + 短期记忆 + 未读批

每次模型调用,上下文固定为三段(这就是 KV 命中的稳定前缀 + 增量):

```
system(人设/画像/风格/边界 + [短期记忆] + [当前时间] + 批次行为规则)
       └ 这段在两次调用间尽量不变 → 命中厂商 KV 缓存
user:  本批未读消息拼接(群聊带 [发送者: xxx] 前缀与 @ 信息)
```

**已读消息永不再现**——它只以"短期记忆摘要"的形式活着(见 §5),对话连续性由此保证,同时天然适配"系统提示前缀稳定 → KV 缓存复用"。

### 2.3 静默(已读不回)

模型读完本批后**允许不产出任何回复**。判定:

- 约定的输出为空、或只含空白/兜底标记(如 `[silent]`)→ 该成员本轮静默;
- 静默 ≠ 失败:照常推进游标、照常调度后续短期记忆任务,不落 AI 消息、不广播;
- 角色级开关 `chatStyle.allowSilent` 可关闭此能力(关闭后空输出按异常重试一次)。

根治"鬼畜":一批只给一次回应机会,回应与否是模型的决定,不是系统的必然。

## 3. 群聊调度规则

### 3.1 消息投递决策

| 条件 | 行为 |
|---|---|
| 用户消息含 `@成员A`(一个或多个) | **点名**:立即为被点名的成员各起一次"轮次"(读各自未读批);未点名成员不受惊动,消息留作其未来攒批内容 |
| 用户消息无 @、或 @全部 | **攒批**:入库待投;到触发时机再投给全体成员(可回应可不回应) |
| AI 成员发言 | 与其他 AI 而言同样是新消息,进入它们的未读批 |
| 手动触发轮次(`POST /groups/{id}/rounds`) | 等价"@全部立即投喂一次",绕过攒批等待 |

### 3.2 攒批的触发时机("不定时")

不承诺固定周期,按以下任一条件触发(全部可配):

1. **静默窗到点**:该会话距最后一条用户消息 ≥ `debounceSeconds`(默认 12s),期间无新消息 → 投喂;
2. **攒批硬顶**:未投喂消息数或字数 ≥ 上限(默认 20 条 / 3000 字)→ 不等静默窗立即投喂(防积压);
3. **群冷却放行**:距上一轮 ≥ `strategy.cooldownSeconds`(默认沿用群配置 30s),避免上一批回应未落地又开一批;
4. **点名**:见 3.1,即时,不占攒批窗口。

新消息到达会重置本会话的静默窗(防抖)。投喂本身是"每成员一次调用",群内顺序执行。

### 3.3 轮次记录(rounds 表)

每轮投喂仍记一条 `Round`(触发人=调度器/点名者,`speakers`=实际发言成员;静默成员不占 speakers)。`round_start / round_message / round_end` SSE 事件沿用。

## 4. 单聊规则

与群聊同一套(这是本设计特意强调的"一对一也是如此"):

1. 用户消息全部入该会话;AI 未读批攒批后投喂,时机同 §3.2(静默窗/硬顶,无冷却限制);
2. AI 允许"已读不回"(比如用户只是随手分享了个表情包/单方面输出);
3. 用户发出的多条消息会**一次性拼接**送达模型,模型对着完整一段话回一次;
4. 单聊无 @ 路由(@ 单聊里按普通文本处理,不回解析)。

## 5. 短期记忆后台任务(KV 缓存对齐)

### 5.1 动机

厂商(如 DeepSeek/OpenAI 兼容端点)对**相同前缀的请求**有 KV 缓存,TTL 内复用可省时省钱。我们的"前缀稳定"设计吃这口红利,代价是:**旧对话只存在于厂商缓存里,本地没有压缩副本**——若缓存过期或上下文被截断,AI 就"失忆"。

对策:每次投喂消费完成后,后台排一个**总结任务**,在 KV 缓存过期**之前**把"上一期短期记忆 + 本批已读消息"压成新的一期短期记忆,落本地库。下次投喂把短期记忆注入 system 前缀 → 即使厂商缓存已过期,本地仍有精华可重建上下文。

### 5.2 字数换算公式(本期拍板)

```
目标字数 ≈ 日期因子 × 原聊天字数 × 换算因子

日期因子   = clamp(1 / (1 + 0.06 × 距今天数), 0.25, 1.0)   // 越旧压得越狠;默认曲线,可配
换算因子   = 0.12                                            // 默认约 1/8~1/10 压缩率;可配
```

- **原聊天字数**:本期参与压缩的源文本字数(上一期短期记忆原文 + 本批消息文本,按 `utf8.RuneCountInString` 计);
- **距今天数**:本批最旧一条消息距今天数,不足 1 天按 1 天计(当天新鲜内容不衰减);
- **取值范围**:目标字数再夹取 `[200, 4000]`,避免过短失义/过长失压缩;
- 示例:本批 3000 字,距今 1 天 → 3000×1.0×0.12 ≈ **360 字**;同批若 30 天前 → 3000×0.36×0.12 ≈ **130 → 夹取 200 字**。

生成 prompt 携带目标字数:"把以下对话压缩为约 N 字的短期记忆,只保留:关键事实/用户偏好/关系事件/未完成话题"。总结结果与参数快照(原始字数、目标字数、日期因子、换算因子、覆盖消息区间)一并落库,便于诊断页审计。

### 5.3 调度时机(先消费、后总结)

| 事件 | 动作 |
|---|---|
| 某成员消费一批(游标推进到 M) | 排定总结任务:`fireAt = now + kvTTLMinutes × 0.8`(默认 TTL 10min → 8min),目标覆盖 `(上次总结游标, M]` |
| 总结任务到点前该成员又有新消费 | 旧任务作废,按新消费点重新排定(厂商缓存已被刷新,总结窗口顺延) |
| 到点且无新消费 | 执行总结(此时仍在厂商 TTL 内);压缩完成后 `chat_short_memories` 更新,覆盖游标推进到 M |
| 成员/会话被删除 | 任务取消,短期记忆随会话级联清理 |

`kvTTLMinutes` 是**保守估计配置**(厂商不公开精确 TTL),默认 10 分钟,可在设置/角色级下调;宁可早总结不可晚总结(早=多一次小调用,晚=缓存过期记忆丢失)。

## 6. 决策记录(评审拍板)

| # | 开放问题 | 决策 |
|---|---|---|
| 1 | "不定时"怎么定 | 防抖静默窗 + 攒批硬顶 + 群冷却,四类触发器(§3.2);不承诺固定周期 |
| 2 | @ 怎么解析 | 发送时按 `@角色名` 精确匹配成员(长名优先,中文标点边界)解析成成员 id 存 `mentions`;请求体可显式带 `mentionIds` 覆盖;解析失败(无匹配成员)视为无 @ |
| 3 | 已读是否永不再投 | **是**:消费即归档,只进短期记忆。上下文=短期记忆+未读批(§2.2) |
| 4 | 日期因子/换算因子 | 默认曲线与 0.12 见 §5.2;换算因子放角色级 `dispatchSettings`,日期曲线常量全局 |
| 5 | 静默表示 | 空输出/空白/`[silent]` 标记判静默;`allowSilent` 可关;静默正常推进游标与记忆任务 |
| 6 | 短期记忆存哪 | 新表 `chat_short_memories`(按 companion+conversation 唯一),滚动覆盖,带 Generation;不混入长期记忆 memories(语义不同,长期记忆仍走召回) |

## 7. 数据模型变更

| 表/实体 | 变更 |
|---|---|
| `messages` | + `mentions` JSON(点名成员 id 列表,仅群聊用户消息有);+ `user_read_at`(用户消息级已读时间,可空);删除草稿结构体 `群聊消息是否已读` |
| 新 `member_cursors` | (conversation_id, reader_id) 主键;reader_id=成员 id 或 `"user"`;`last_read_message_id`=已读到哪条(消费水位);`updated_at` |
| 新 `chat_short_memories` | (companion_id, conversation_id) 主键;content 本期摘要;raw_chars/date_factor/ratio/target_chars 参数快照;covered_from_id/covered_to_id 覆盖区间;generation;summarized_at |
| `companions.chat_style` | + `allowSilent bool`(默认 true) |
| `companions` 新嵌 `dispatch_settings` | `debounceSeconds`(12)、`maxBatchCount`(20)、`maxBatchChars`(3000)、`kvTTLMinutes`(10)、`charRatio`(0.12,换算因子) |
| `groups.strategy` | 语义微调:冷却/轮次继续用于攒批投喂节奏;`enabled` 仍只约束"主动起话题" |
| `rounds` | 语义扩展:轮次=一次批次投喂;静默成员不记入 speakers |

模型现状提示:`messages.id` 在重构后是 gorm 自增 uint,同一会话内按 id 单调增,正好支撑游标水位;跨会话删除/清空不影响(游标按会话维度查询)。
