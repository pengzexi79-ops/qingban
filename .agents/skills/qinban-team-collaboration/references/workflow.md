# 分支、PR 与验收流程

## 1. 任务卡与技术确认

开始开发前必须有：

```text
任务编号：QB-领域-序号
产品负责人：总指导
执行角色：frontend-core / frontend-chat / frontend-experience / backend-lead
负责人：GitHub 用户名
产品目标：一句话
验收标准：可观察、可测试
明确不做：
允许修改：精确到目录或文件
禁止修改：明确写出
接口影响：无 / 请求契约 / 已冻结契约
依赖任务：无或任务编号
热点文件认领：无或文件列表
技术负责人确认：待确认 / 已确认
```

前端任务在“技术负责人确认”为待确认时，AI 可以查看代码、出实现方案和列接口需求，但不能改代码。

## 2. 分支

仓库主干是 `master`，不是 `main`。

```bash
git fetch origin
git switch master
git pull --ff-only origin master
git switch -c fe-chat/QB-CHAT-001-message-scroll
```

建议前缀：`fe-core/`、`fe-chat/`、`fe-exp/`、`be/`、`docs/`、`fix/`。

一个分支只对应一个任务卡。禁止在已经混有其他工作的分支上继续追加功能。每名前端同时最多保留 1 个进行中的编码任务；前一个任务进入审核或明确暂停后，才领取下一个。

## 3. 开发与提交

- 前端先按技术负责人冻结的方案实现，不自行扩展技术范围；
- 后端先冻结契约，再实现服务端；
- 小步提交，不把整个仓库格式化混进功能；
- commit 前执行 `git diff --check` 并人工检查所有变更文件；
- 每轮有意义的修改完成后，AI先根据实际 diff 生成独立开发保存点档案；代码和档案一起进入当前分支。
- AI 只有收到当前成员明确要求时才 commit 或 push。

## 4. 最低测试

纯前端：

- 桌面和移动宽度各检查一次；
- 页面无整体溢出，聊天等长内容只在内部滚动；
- 浏览器控制台无新增错误；
- 关键点击链路可操作；
- 修改过的 JavaScript 通过语法检查；
- 不真实消耗付费 API，除非总指导明确授权。

后端：

- `gofmt`；
- `go test ./...`；
- 条件允许时 `go vet ./...`；
- 检查路由、错误码、幂等、迁移和密钥脱敏；
- 新接口同步 OpenAPI、Bruno 和必要测试。

如果环境缺少依赖，必须写“未执行”及原因，不能伪装成通过。

## 5. PR 双门禁

所有代码 PR 采用两类门禁：

1. **产品门禁**：改变产品方向、页面流程、文案定位或验收目标时，由总指导确认。
2. **技术门禁**：所有前端和后端代码最终由 `backend-lead` 判断能否合并。

具体规则：

- 前端 PR：前端成员可先互相做体验检查，但不能代替 `backend-lead` 技术审核；PR 应保持单一目标和可快速审阅，过大时由技术负责人要求拆分。
- 后端负责人的 PR：必须包含测试结果、自审清单、契约影响和回滚方案；因团队没有第二名同级后端，由他自行做最终技术判断，总指导确认没有偏离产品范围。
- 跨前后端 PR：原则上退回拆分。
- 总指导自己写的前端代码也不能绕过技术门禁。
- PR 描述必须列出本 PR 包含的保存点档案相对路径，审核者据此核对代码、测试和影响说明。

合并固定使用 **Squash and merge**。默认由 `backend-lead` 合并；他可以明确授权他人合并已批准的纯前端 PR。

## 6. 处理主干更新与冲突

不用 rebase。功能分支落后时：

```bash
git fetch origin
git switch 当前功能分支
git merge origin/master
# 解决冲突并重新测试
git add <冲突文件>
git commit
git push
```

冲突由分支负责人先处理；涉及架构或接口冲突时由 `backend-lead` 裁定，不让 AI 自行选择一边覆盖。

## 7. 禁止操作

- 直接 push `master`；
- force push 主干或共享分支；
- reset/clean 掉未知改动；
- 修改别人的分支；
- 未经技术负责人确认同时编辑热点文件；
- 前端自行改框架、依赖、API、数据库或后端；
- 一个 PR 混入无关重构、品牌改名、依赖升级或大范围格式化；
- 把假数据、占位路由或 TODO 描述成已经完成。

建议管理员为 `master` 开启：Require a pull request、至少 1 个 approval、阻止 force push、会话必须解决、必要状态检查。配置仓库保护属于管理员操作，AI 未经明确授权不得修改。
