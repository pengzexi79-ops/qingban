# 存档格式与规则

## 1. 路径

每个保存点独立生成：

```text
docs/development-archive/YYYY-MM-DD/YYYYMMDD-HHmmss-fff-角色-成员-任务编号.md
```

不维护一个所有人共同追加的总日志，避免多人分支频繁冲突。Git 历史和按日期目录就是索引。

## 2. 必填内容

每份档案必须包含：

- 生成时间；
- 成员与执行角色；
- 任务编号；
- 当前分支和基准提交；
- Git 检测到的变更文件与状态；
- 本保存点目的；
- 根据 diff 总结的具体变化；
- API、数据库、配置和兼容影响；
- 实际执行的测试及结果；
- 风险、未完成事项和下一位负责人；
- `git diff --check` 结果；
- 非存档变更文件生成的 `change_fingerprint`，用于识别重复保存点。

## 3. 内容质量

合格：

```text
聊天区域改为 flex 容器，消息列表承担内部滚动；移动端输入框保持在视口内。
```

不合格：

```text
优化代码。
更新了一些文件。
功能已完善。
```

AI 只能根据当前 diff 写事实。未执行测试要明确写“未执行”及原因，TODO、空实现、模拟数据和 501 路由不能记成已完成能力。

脚本会忽略日期目录下已经生成的档案，以当前分支、任务编号、基准提交以及非存档变更文件的路径和内容计算指纹。同一任务上下文中的同一变更状态已经有档案时拒绝重复生成；继续修改后指纹变化，才会创建下一个保存点。

## 4. 角色越界

脚本会对明显的前后端跨界进行阻止：

- `frontend-*` 修改 `backend/**`、`bruno/**`、服务端测试或 OpenAPI/Phase 1 契约；
- `backend-lead` 修改 `frontend/**`；
- `director` 直接修改前后端业务代码。

确有跨界任务时，必须由 `backend-lead` 明确批准，并在调用脚本时加入 `-TechnicalApproval`，同时在档案的影响说明中记录批准原因。

## 5. 修正历史

已经合并的档案不得改写。如果旧档案错误，创建新任务编号或使用原任务编号加 `-CORRECTION`，在新档案中引用旧文件并说明更正内容。
