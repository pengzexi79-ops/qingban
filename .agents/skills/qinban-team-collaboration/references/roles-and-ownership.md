# 角色、权力与文件归属

## 1. 双负责人模型

| 领域 | 最终负责人 | 最终决定 |
|---|---|---|
| 产品 | `director`（总指导） | 做什么、优先级、用户体验目标、验收标准、不做什么 |
| 技术 | `backend-lead`（后端大佬） | 怎么实现、架构、接口、数据库、安全、依赖、测试、冲突与是否可合并 |

任何成员或 AI 都不能把产品权力和技术权力混为一谈。总指导可以否决不符合方向的功能；技术负责人可以否决不安全、不可维护或破坏架构的实现。

## 2. 总指导：`director`

负责：

- 产品定位、功能优先级、页面范围、交互方向和最终产品验收；
- 决定有争议需求是否做、何时做；
- 冻结品牌为“亲伴 / QinBan”；
- 给每个任务写清目标、验收和不做项。

总指导不直接裁定后端结构、数据库索引、Go 包结构、模型协议等技术细节。总指导亲自做前端时，需同时选择一个 `frontend-*` 角色，其代码与其他前端一样交给 `backend-lead` 审核。

## 3. 三名前端：AI 氛围编程执行者

共同规则：

- 使用 AI 加快页面实现，但只能在技术负责人批准的架构、文件和接口内开发；
- 不自行升级框架、拆目录、引入状态库、改构建链或发明后端字段；
- 不以“页面能显示”代替可维护性、错误处理和接口兼容；
- 对技术负责人的修改意见继续在原分支整改，直到批准。

### `frontend-core`

主要范围：应用壳、导航、响应式、设计系统、共享组件、前端模块化、经批准的 API Client 封装。

### `frontend-chat`

主要范围：会话、聊天、通讯录、AI 好友、群聊、记忆页面及对应前端状态。

### `frontend-experience`

主要范围：朋友圈、我的、设置、API 配置、模型能力展示、用量、本地数据管理。

三个前端的逻辑角色可按成员能力调整，但技术负责人必须先确认实际文件边界。

## 4. 技术负责人：`backend-lead`

`backend-lead` 是全项目技术总负责人，而不只是“写后端的人”。负责：

- 确定前后端技术路线、目录和模块边界；
- 拆分可并行任务并分配共享热点文件；
- 定义和冻结 API、错误码、数据结构与兼容策略；
- 编写后端、数据库、模型调用、安全和测试；
- 审核所有前端代码 PR，提出必须修改项；
- 判断测试证据是否足够、是否允许合并；
- 处理技术冲突并向总指导说明成本和产品影响。

独占或最终审核范围：

- `backend/**`
- `build/**`
- `tests/**` 中的服务端测试
- `bruno/**`
- `docs/openapi.json`
- `docs/openapi.yaml`
- `docs/openapi.phase1.yaml`
- `docs/PHASE1_API.md`
- 数据库结构、迁移、服务端配置、密钥保护、模型供应商、消息与记忆流程

只有一名具备传统工程能力的技术负责人时，不要求前端成员假装能够审核其后端内部实现。后端负责人自己的 PR 可以在测试通过、写明自审结果、契约影响和回滚方案后自行做最终技术判断；总指导只确认产品范围是否偏离。

## 5. 共享范围

以下文件必须在任务卡中写明原因，并取得技术负责人同意；涉及产品方向时同时由总指导确认：

- `README.md`
- `AGENTS.md`
- `.github/**`
- `.agents/skills/**`
- `docs/BACKEND_HANDOFF.md`
- `.gitignore`
- 框架、依赖、构建配置和公共数据结构

## 6. 当前前端热点文件

- `frontend/index.html`
- `frontend/js/app.js`
- `frontend/js/store.js`
- `frontend/css/style.css`

由 `backend-lead` 维护热点文件占用表。同一时段一个热点文件只能有一个任务分支修改。禁止三个 AI 分别修改后交给后端负责人手工拼接。

三名前端长期并行前，建议由 `frontend-core` 按技术负责人批准的方案做一次纯模块化 PR，至少分离：

```text
frontend/js/core/
frontend/js/features/chat/
frontend/js/features/companions/
frontend/js/features/groups/
frontend/js/features/memory/
frontend/js/features/moments/
frontend/js/features/settings/
frontend/js/services/
frontend/css/core/
frontend/css/features/
```

模块化 PR 不得同时改变产品功能、API 字段或视觉方向。完成并验证行为一致后，再由技术负责人分配三个前端的目录。

## 7. 跨角色变更

- 前端需要接口：提交需求、UI 状态和降级方案，由后端负责人定义最终契约。
- 后端改变接口：先冻结契约并通知受影响前端，再实现，最后由前端消费。
- 一个任务同时触碰 `frontend/**` 和 `backend/**` 时，原则上拆成两个关联 PR。
- 技术方案有分歧时听 `backend-lead`；产品取舍有分歧时听 `director`。
- 紧急修复无法拆分时，任务卡必须列出负责人、允许路径、测试和回滚方式。
